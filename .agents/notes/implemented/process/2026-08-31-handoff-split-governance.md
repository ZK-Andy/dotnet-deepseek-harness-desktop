# Agent Note: handoff-split-governance

Status: implemented

## Problem

HANDOFF.md（交接主文档，gitignore 本地工作文档）在 2026-08-27 结构拆分（docs-management-tiering 第 1 层：叙事/决策分层 + 有界滚动窗 + journal 归档）后再次膨胀：156 行/3633 词 → 170 行/3955 词（约 +9%），且结构性问题依旧——**膨胀压力从未被机制真正约束，只是被推迟**：

1. **滚动窗门禁上限（40 条）远大于实际习惯**（~11 条/会话批次）→ 归档压力永不触发，窗口只进不出；
2. **门禁只有条数上限，无条目长度/体积约束**——session-close 卡第 7 步明确定义「精条目」（日期｜类型｜ADR 一行主题｜commit｜README 结论一行），实际条目却是 800–1400 字的会话流水账（21 条共 ~1515 词，最长 1372 字），纪律零机器兜底；
3. **待办区无生命周期**——`[x]` 勾销只打勾不压缩内容，完成项细节（ADR/滚动窗里都有）原样堆积；`[ ]` 项写全描述而非指针。待办区 62 行 1847 词 = HANDOFF 最大单块（47%）。

结论：上一轮瘦身的手段（存档旧条目）有效但机制不完整——缺**每类内容独立的体积预算 + 机器强制 + 生命周期自动收紧**，复发是必然。

## Decision

**职责拆分两文件 + 记录窗摘要化 + 机械预算**（用户 2026-08-31 拍板：方案 B + ≤2 行摘要 + 组件保持 gitignore）。已落地：

1. **`HANDOFF.md` 收缩为入口/稳定区**：背景、位置、当前状态、开始步骤保持原地（~200 词）；「交接更新记录」降为**摘要滚动窗**——21 条全压缩为 ≤260 字/条（日期｜类型｜commit/ADR 指针｜一句话结论），全文下沉 journal；「待办」节降为一行指针。
2. **新增 `HANDOFF-todos.md`（行动区独立）**：全部待办迁入——`[ ]` 8 条压缩为 ≤340 字（保留触发条件与指针）、`[x]` 31 条压缩为 ≤220 字一行指针（标题/日期/commit/ADR）；gitignore 新增 `/HANDOFF-todos.md`。
3. **`verify-handoff-structure.py` 升级为跨文件门禁**：窗口条目 ≤24 且每条 ≤260 字；todos 文件必须存在且被「待办」节引用（相对链接）；`[ ]` ≤16 条且 ≤340 字、`[x]` ≤220 字、总条数 ≤70；`--self-test` 扩至 11 用例。
4. **工作流卡与规则引用同步**：session-open 步骤 1 / session-close 步骤 3 / AGENTS 质量门行 按「HANDOFF.md（入口）+ HANDOFF-todos.md（待办）」两文件口径更新。
5. **归档**：21 条现行条目全文追加至 `.plan/journal/2026-08-session-journal.md`（「2026-08-30/08-31 批次」节），叙事不丢、决策本就在 durable 四家。
6. **顺手修复 verify-md-links.py 的文档契约漂移**：AGENTS 质量门注释声明「.plan/ 排除」而脚本未排除；归档条目自仓库根搬进 `.plan/journal/` 后相对 ADR 链接解析错位（md-links 报缺目标）——脚本补 `.plan` 排除段，并把本批归档的 2 条 ADR 链接改为根绝对形式（`/.agents/notes/…`）供人读可点。

## Alternatives considered

- **方案 A：不拆文件，纯机制治理**（只收紧滚动窗上限/条目长度 + 完成项压缩）：落败——单文件仍混合三类生命周期（稳定/行动/记录），任一类的自然增长都会再次顶开共享预算，治理又一次「先瘦后胖」。用户已选 B。
- **方案 C：拆三文件（status/todos/window 全分离 + 入口纯索引）**：落败——新会话恢复上下文要先跳 3 个文件，摩擦最大，收益边际递减；稳定区（~200 词）与记录区（收紧后 ~600 词）没有独立预算的必要性，B 已覆盖全部痛点。
- **组件文件纳入 git 跟踪**（获得 verify-md-links 免费链接校验 + 版本史）：落败——与 docs-management-tiering「本地工作文档不提交」既有一致决定冲突；交接文档的高频易失性正是第 3 层（会话记忆快照保护，触发条件 = 丢过数据）的管辖范围，当前知情接受。用户已选保持 gitignore，链接校验自建进 verify-handoff-structure.py。
- **仅收紧 session-close 纪律、不加门禁**：落败——08-27 已有「精条目」定义仍被违反，靠人自觉无机器兜底必然复发（HANDOFF 膨胀的原始成因，docs-management-tiering 已记录同款教训）。
- **滚动窗删除、完全以 journal 索引代替**：落败——失去「读 HANDOFF 即知最近发生了什么」的交接价值；摘要窗口（≤260 字/条）以 ~1.3K 词保留该价值，是取舍最优。

## Consequences

- **现状基线**：HANDOFF.md ~87 行 / ~820 词（稳定区 + 22 条摘要），HANDOFF-todos.md 39 条（8 `[ ]` + 31 `[x]`）；总量低于 08-27 瘦身后水平，且三类内容各有独立预算、机器强制。
- **预算与生命周期**：窗口超 24 条或单条超 260 字即门禁 FAIL（fail loud 提示归档）；勾销完成项须压缩为一行指针、`[ ]` 超 16 条须清账——预算即纪律，复发由门禁拦截而非靠自觉。
- **风险与缓解**：压缩可能丢行动信息 → `[ ]` 条强制保留触发条件/复验时机要点，逐条对照旧文核对；摘要过度损失交接价值 → 摘要保留「发生了什么 + ADR/journal 锚点」；门禁误伤 → 预算按单行物理长度度量、给出明确上界，超限时拆行/删冗余而非放宽。
- **journal 链接纪律**：`.plan/` 现不入 md-links 校验面（与 AGENTS 注释一致）；归档条目若含仓库内链接，写根绝对形式（`/…`）供人读可点。
