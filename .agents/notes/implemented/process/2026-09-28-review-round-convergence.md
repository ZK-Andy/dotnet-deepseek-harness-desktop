## Problem

[feature-flow](../../../workflows/feature-flow.md) 步骤 5 用密集的机器门规定义了**怎么开一轮评审**（[简报门](../../implemented/process/2026-09-04-review-brief-gate-self-assertion.md)、[冻结门](../../implemented/process/2026-09-13-review-freeze-worktree-discipline.md)、[档位门](../../implemented/process/2026-09-03-review-tier-escape-proofing.md)、门禁自证行），却没有定义**怎么关一轮**：关于修复后如何重审，全文只有一句「修复轮重启前重新冻结」，它默认你会重启整轮；证据行要求 `R1=ok R2=ok R3=ok`，而 `ok` 在文本与脚本里都没有定义。2026-09-28 的 B-2 批（三平台打包三流合一，暂存集 34 条）实测出五个后果：

- **滚 4 轮、约 10 次代理运行、0 次提交**：第 1 轮抓到两条真缺陷（`actions/checkout` 收进本地 composite → 五条腿齐死；被调用 workflow 的 `concurrency` 组名与调用方同组死锁、与直调预览共享组误掐发布轮），此后 9 个 Blocker 全是文案（勘误计数残留、`PrepareActions` 归因、ADR 与 cookbook 口径互斥）。
- **轮次发散而非收敛**：R1 报出的 Blocker 数是 `3 → 1 → 2 → 3`，R2 是 `1 → 0 → 1 → 2`。机制是评审对象只增不减——四轮共用同一 `base`（批基提交），暂存集从 13 条长到 34 条，每轮都在重读全批而非上一轮的增量。
- **简报把「再扫一遍」写成常驻项**：每轮定向检查都带「收窄复扫」；在一个持续变大的集合上做新鲜扫描，必然产出新条目——发现数由构造决定，不由缺陷决定。
- **R3 被饿死**：三路简报必须齐（门禁要求）却限最多两路并发，R3 被反复后置、三轮未产出结论；而 FULL 证据行要求 `R3=ok`，于是整批卡在「无 `Review:` 行 → 不可提交」。
- **一条错误的评审结论值两轮**：第 2 轮报告给出的两条机制归因（`concurrency` 三段各自作用、`action.yml` 读取时机）本身是错的，被写进 `package.yml` 注释、ADR、cookbook 三个家；第 3、4 轮整轮用于拆掉它们——同一主张有多个家时，错误结论按家的数量放大。

## Decision

一、**收口判据**：本轮范围内 0 Blocker 即收口。Suggestion 由主会话逐条书面裁定（采纳/驳回/部分采纳 + 理由）后收口，**不得为 Suggestion 再开一轮**；证据行 `R*=ok` 的语义即「该路本轮 0 Blocker 且建议已书面裁定」（形制不变）。

二、**轮次有界**：每路每批 ≤3 轮（首轮 + 最多两轮验轮）；第 4 轮起 `verify-review-brief.py --enforce` 拦下，仅用户显式授权（简报带非空「轮次授权：」行，**该行须行首、可带 `-` 列表符号**）才可开——规则原文本身含此字样，子串匹配等于「把规则抄进简报即获授权」（本批 R3 评审实测）。**轮次自证须互校**——轮次只由文件名后缀取值，故另设两条防降级：标题声明的轮次（`第 N 轮`）与文件名后缀不一致即判红；带 `## 上一轮结论的处置` 段而轮次 < 2 亦判红（处置段本身即验轮声明）。缺此互校则「去掉文件名后缀」是一条静默降级通道：以批基为 `base` 的验轮会绕过第四条的全部判据（本批 R2 评审实测该形态原先放行）。

三、**验轮只核处置**：轮次 ≥2 的简报必须带 `## 上一轮结论的处置` 段（按**行首二级标题**认，且段内须有条目——纯子串会把正文里对该段名的引用算作段存在，空段等于没写处置）；只重开上一轮报了 Blocker 的路；定向检查只写「处置是否闭合」，禁「收窄复扫/有无新发现」类条目。验轮报出的新问题转下批或挂账，只有「修复引入的新缺陷」计入 Blocker 并须当轮修。

四、**验轮审增量**：每轮冻结后立即 `git write-tree` 记下本轮评审对象的 tree——`verify-review-brief.py --enforce` 在冻结通过时会打印它，记下即用；轮次 ≥2 的简报 `base:` 必须是该 tree，评审 diff = `git diff <上一轮 tree> --cached`。门禁据此校验两条：`base` 的对象类型必须是 `tree`（拦下「直写批基提交」这一自然误用——`git cat-file -t <批基>` 得 `commit`；但挡不住刻意写 `<批基>^{tree}`，那与「错写另一个 tree」同属下面第五条记的信任面），且相对该 tree 的增量非空（增量清零 = 没有待验修复）。

五、**三路须在同一轮内跑完**：并发上限两路只是分批，不得跨轮补跑；任一路被无限期后置即整批卡（无 `R3=ok` 即无 `Review:` 行）。**此约束作用于首轮**；验轮按第三条只重开上一轮报了 Blocker 的路，未报的路在本轮不起跑、其 `ok` 沿用上一轮（否则第三条与本题按字面互相矛盾）。

六、**报告里的机制/因果断言在写入 ADR/注释前必须被证实**（未证实的标「推演」），同一主张只写一个家、其余留指针。

七、落点：[feature-flow](../../../workflows/feature-flow.md) 步骤 5 新增「收口契约」条、冻结条补 tree 快照；[review-scope-narrowing](../../implemented/process/2026-08-31-review-scope-narrowing.md) §4.1 简报模板加「上一轮结论的处置」段与轮次字段、§4.2 加验轮收窄基线；`scripts/verify-review-brief.py` 落机械判据（自测 9 → 15 例）。

## Alternatives considered

- **改证据行格式（如 `R1=ok(0B)`）让「0 Blocker」可机读**：落败——证据行是全仓 91 篇笔记共用的形制，改形制要么把既有行判非法、要么引入双格式判别；且「0 Blocker」是**报告面**结论，报告不落盘，门禁看不见报告，改形制也换不出真判据。改为在文本里定义 `ok` 语义，形制不动。
- **验轮基准用「上一轮修复提交」而非 tree**：落败——FULL 批次的提交被档位门要求携带 `Review:` 行，而该行要等全部轮次收口才写得出，「修复轮先提交」与「证据行」互相等待成死锁（B-2 现状即此：修复只能留在暂存集）。tree 对象不需要提交、不触发任何 hook，且同样是精确的增量基准，还能由门禁直接打印。
- **轮次上限取 2（首轮 + 单验轮）**：更贴合「禁止反复审」，但「验轮发现修复本身引入新缺陷」这一正当形态会被拦死。取 3 留一轮纠错余地，第 4 轮起须用户点头——B-2 正好卡在被拦的第 4 轮。
- **不引入 tree，改为要求简报逐条声明本轮改动清单**：落败——那是现状（第 2 轮起的简报用散文列改动面，因为「修复轮未提交，`git diff` 看不到增量」）；散文清单既不可机校、也不构成增量基准，评审代理只能按散文重读全批。
- **验轮禁止一切新发现（含修复引入的新缺陷）**：落败——修复引入的缺陷必须当轮修，否则把已知缺陷放过门；故只把「复扫型新发现」转下批，保留该例外。
- **[档位门](../../implemented/process/2026-09-03-review-tier-escape-proofing.md)按增量重定档（纯文档增量落 LIGHT）**：本可再省两路，落败——FULL 是**批次**语义（批内任一 FULL 路径命中即整批三重审），按增量重定档会让「第一批只报 Blocker 才动手改的那两行」成为免审入口；收敛改由「轮次上限 + 增量审 + 处置段」承担。`docs` 为无条件 FULL 触发面同理不动（docs 承载契约口径）。
- **把轮次判据放进 pre-commit/CI**：落败——简报是本地 gitignore 工作档，CI 无工作树语义（与冻结判据同因）；执行点只能是评审启动闸。
- **让评审代理输出结构化轮次报告（落盘 JSON）供门禁读**：落败——门禁只能看见文件，而要存的是「上一轮报了几个 Blocker」这类会话内事实；为它引入一套报告落盘格式与清理策略，成本远超它替代的那一次人工转写（该面记为未覆盖边界）。

## Consequences

- 收益：轮次由构造收敛——验轮只核处置、只审增量、且有硬上限；**推动「每轮重读全批」的那个结构件被拆掉**（`base` 必须是 tree，`base..index` 成为唯一审面），B-2 实测的 `3 → 1 → 2 → 3` 发散形态失去原有成因。注意「定向检查不得写复扫/新发现」仍是散文禁令、无机器判据（见未覆盖④）。
- 收益：R3 不再被无限期后置（三路须同轮起跑），「三路齐 ok」与「无证据行即不可提交」之间的死锁关闭。
- 代价：忘记在冻结时 `git write-tree` 会让**下一轮**没有可用的 `base`——该 tree 只能由冻结时写出，索引一移即不可重建（本轮自身不因此失败）。为此 `--enforce` 每次打印本轮 tree，把它从一次记忆变成一次复制；**取不到即 fail loud**（原先只在无违规分支打印 tree、取不到就静默放行，恰好丢在最该示警的时刻）。另：冻结告警不吞轮次违规——一次运行给出两类违规的全集，不必跑两遍才凑齐。
- 边界：规则上线时已在审批次的转入——本批即首例：其 R1/R2 首轮冻结时本契约尚未上线，`.review-briefs/` 无 `-r2` 简报、脚本也未为该批打印 tree；若要给该批开验轮，`base` 只能用**首轮冻结时**手工记下的 tree（本批为 `3d7086ea77617dc563a3b994d5b1e0a59bc303fa`），否则只剩「写成批基」或「增量清零」两个错误出口。此后各批按第四条自然成立。
- 代价：第 4 轮起需要用户在场（写「轮次授权：」行）；无人值守的长任务在超限处停下并交出「还剩哪些 Blocker」清单。
- 边界：判据只能证明「`base` 是 tree 且增量非空」，证明不了该 tree **就是**上一轮评审对象的快照（错写另一个 tree 不会被发现）——刻意的信任面，与档位/冻结/自证诸门同级，靠简报写实数 + 评审代理复核。
- 边界：上限按**路**计不按批计；三路各自可到第 3 轮，合计仍是 9 次代理运行的硬界。
- 未覆盖（另立项）：①「把已删文件名当现行落点断言」的勘误扫描无机器门（本批 16 处 `Erratum:` 行靠评审两轮才找齐），补门禁会牵出存量 remediate 面，需独立评估；②评审报告不落盘，「哪一路报了几个 Blocker」机器不可读，收口判据仍靠主会话如实转写；③`docs` 为无条件 FULL 触发面（文档增量也开三路）；④「验轮定向检查不得含复扫/新发现类条目」无机器判据（门禁只数 1–5 条），仍靠简报人写 + 评审代理独立判读。
- 与 B-2 批的关系（[三流合一](../../implemented/process/2026-09-28-ci-package-workflow-unification.md)）：该批即 Problem 段的病例，最终按既有门规落地——主体 `c93bd4c` 引入其 ADR 头部的 `Review: FULL/2026-09-28#3/R1=ok R2=ok R3=ok`，证据回写 `d38584e` 另带 `Review: LIGHT/2026-09-28#2/R2=ok`（两者不是同一批的同一行）；R1/R2 各 4 轮后由用户按「0 Blocker」口径叫停续轮、R3 首轮报 1 Blocker 修后按同一口径收口；其末轮清单因评审报告不落盘而无法重建，正是未覆盖②的第二次实付代价。

## Testing

- `python3 scripts/verify-review-brief.py --self-test`：15 例夹具全绿——原 9 例 + 新增六例：①验轮缺处置段判红／补上转绿；②`-r4` 无授权判红／带非空授权转绿；③真 git 仓库上「`base` = 批基提交」判红、「`base` = 上一轮冻结 tree 且增量非空」转绿、「`base` = 当前暂存集 tree（增量清零）」判红；④标题声明「第 2 轮」而文件名无后缀判红／标题不带轮次令牌转绿（轮次自证互校）；⑤首轮带处置段判红／验轮带空处置段判红；⑥漂移 + 批基 `base` 的**同一次**报告里冻结与轮次两类违规都在（互不吞没）。每条新判据的放行侧与判红侧同批在位，防恒真。
- `python3 scripts/verify-adr-format.py`、`verify-md-links.py`、`verify-doc-budgets.py --manifest scripts/doc-budgets.manifest.json` 全绿（`.agents/workflows/feature-flow.md` 无字数预算条目）。
- 轮次判据的执行点只在本地评审启动闸（`--enforce`），与冻结判据同因不进 CI；CI 面不新增执行点。
