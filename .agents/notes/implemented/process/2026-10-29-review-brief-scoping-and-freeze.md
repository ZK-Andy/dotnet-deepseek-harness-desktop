# Agent Note: 评审简报限界与评审对象物理隔离

Status: implemented

Review: FULL/2026-10-29/R1=ok R2=ok R3=ok

增量闸豁免：gross ≤ 1100，fanout ≤ 15，packages ≤ 1（一次性：本批与「随包插件版本 bump 闸」共用同一工作树，两个独立变更合计 gross 777——其中 398 行是那个闸的整份新脚本，本批自身 379；拆批会让两篇 ADR 互相引用断链，且两个变更都要动 `scripts/verify-*.py` 与同一批 hooks/CI 接线，拆开必有一半处于不可用中间态）。`file` 与 `newfile` 两帽未放宽：已分别压到 150/150 与 398/400。

## Problem

2026-10-29 的「随包插件版本 bump 闸」批次，三路评审在同一小 diff 上反复发散：65 行增量的验轮跑了 42 分钟且零产出（被迫中断），另一路在已修好的计数上白报一条 Blocker，第三路自述「我开工时 tree 是 `526b299`，中途变成 `129c1f4`」后给出「冻结版 / live 版」两套结论。

三个根因都在**简报的形状**与**冻结的执行方式**上，不在评审代理的判断力：

1. **阅读面无边**：`需深审面（精读，逐行判读）：<文件清单>` 只写文件名。8 行改动配一份全文精读授权，代理没有理由停在增量里。
2. **检查项是问句**：`<检查项 1：要验证什么 + 证据位置>` 实测写成了「是否会被误命中？」「会不会静默缩小？」。问句没有封闭答案集——每个问句都是一个开放的探索方向，答完一个还有下一个。
3. **报告容器无界**：`返回 Blocker[]/Suggestion[]`。任何观察都能以 Suggestion 合法塞进去，且验轮没有「只填处置表」的形状。
4. **冻结靠自律**：`verify-review-brief.py` 只在**出发前**校验工作树冻结。2026-10-29 实测：执行者在 R3 仍在运行时两次改动在审文件（一次修 R2 的 Blocker、一次修 R3 自己的 Blocker），R3 只能锚定旧 tree。门禁抓不住，因为它在代理返回后不再运行。

第 4 条是本批最严重的一条：**它让前三轮的评审结论都只对旧对象成立**，等于花了三轮时间验证一个已经不存在的对象。

## Decision

四条判据全部前移到**签发简报时**，加一条执行方式的物理改造。

1. **hunk 锚点**：`需深审面` 的每条须写成 `<文件>:<起>-<止>`（或 `<文件>:<行>`）；只写文件名即判红。阅读面在出发时就被切到行区间。
2. **断言表取代问句**：`Directed checks` 每条须是 `- [ ] A<N> <命题> ——证据：<文件:行>或<命令>`。编号让答案集成为键集（A1/A2/…），问句形态（无证据锚且以「？」收尾）判红。代理要回答的问题在出发时固定。
3. **时间盒 2 分钟**：简报须带 `时间盒：2 分钟`，上限 2。超时即该路不合格，无产出按未审计计（沿用「中断即未审计」铁律）。这是用户 2026-10-29 的明确裁决。
4. **验轮报告容器封闭**：验轮 `Report contract` 只留「填处置表」——表长 = 上一轮条数，**无「新发现」字段**；出现该字段即判红。新问题转下批。
5. **评审对象物理隔离**：新增 `verify-review-brief.py --export <dir>`——把冻结 tree 包成悬空 commit 后检出为 detached worktree，**只把该目录交给代理**。主工作树后续改动碰不到它。冻结从自律换成文件系统事实。

前四条由 `verify-review-brief.py` 机械强制（自测新增 6 个负向夹具，各自对应一条判据）；第 5 条是执行方式，`--export` 打印目录与 tree，`feature-flow` 步骤 5 与 `review-scope-narrowing` §4.1 同步改写。

## Alternatives considered

- **在代理返回后校验报告（schema / 重跑冻结门禁）**：落败——用户 2026-10-29 的原话：「都返回了你限制有什么意义呢？重复跑不通过，一点返回没有」。事后拦截否定一次已经花掉的成本，不产出任何东西；且冻结门禁在返回后重跑，抓到的是执行者本人，等于把纪律问题伪装成技术问题。
- **加「禁止发散」的散文指令**：落败——简报里本来就写着「只审增量、不做复扫、不找新问题」，实测无效。禁令不是形状；形状才约束行为。
- **给子代理发消息让其收敛**：落败——中途介入会污染报告独立性（`R3=ok` 将无法区分「它判定没问题」与「它照办收窄了」），且这正是被否掉的事后补救的另一种形式。
- **依赖 `workflow` 工具的 schema 校验输出形状**：落败——schema 只能约束形状、约束不了内容质量（`evidence` 字段仍可写未跑过的断言）；且它同样是返回后校验。
- **只做物理隔离、不改简报**：落败——隔离只治根因 4。前三轮的发散中，有两条（计数重复报、双套结论之外的口径外溢）在对象稳定的情况下照样发生。
- **把冻结门禁改成后台常驻监视**：落败——监视到的违规已是既成事实，且需要常驻进程；`--export` 用一次性命令达成同一目的且更彻底（对象根本不在主工作树里）。
- **放开时间盒到 5–10 分钟**：落败——42 分钟零产出的对照说明问题不是分钟数而是无界；2 分钟逼出「简报必须先封闭任务」的前提，超时本身也是判据。

## Consequences

- 收益：发散的四条入口在简报签发时全部封死；评审对象不可能再漂移。举证：新判据在写好后立刻把本批三份旧简报判红 32 条，说明它们确实不满足新形状。
- 代价：**简报变重**。写一份合规简报要先算 hunk 行区间、编号断言、写时间盒；主会话的准备工作从「列文件」变成「列行 + 立命题」。这是刻意的成本转移——准备工作从评审代理的探索时间里扣。
- 代价：**2 分钟太紧**可能逼出误判。缓解：超时判「不合格」而不是「不通过」——该路作废、换一轮，不是把错误结论写进 `Review:` 行。若反复超时，正确反应是把批次拆小或把任务写得更窄，不是放宽时间盒。
- **断言表可能固化错误前提**：如果主会话写了一条基于误解的断言，代理会照答「成立/不成立」而不会指出命题本身有问题。缓解：`Explicitly out of scope` 里保留一条「断言命题本身可质疑，指出即算 Blocker」。
- **物理隔离的副作用**：`.review-object/` 是一个完整工作树副本（本仓约 200MB 含构建产物目录），需要 `git worktree remove` 清理，否则 `git worktree list` 会累积 `prunable` 条目。已加 gitignore；清理责任在收尾。
- **未覆盖面**：判据管形状不管内容——`证据：<文件:行>` 后面那句可以是未跑过的断言。这需要另一条规则（证据须是可复现命令及其输出），本批未做。

## Testing

- `python3 scripts/verify-review-brief.py --self-test`：16 个夹具全绿。新增 fixture 16 系列逐条对应新判据：无 hunk 锚点、问句形态、缺证据锚、缺时间盒、时间盒超限、验轮保留「新发现」出口——各自判红；正例（合规简报）放行。
- 新判据对本批旧简报的实跑：「32 violation(s)」，其中 hunk 4 条、断言表 5 条、时间盒 3 条，均为真实违例而非误报。
- `--export` 实跑：导出目录含完整评审对象（`scripts/verify-bundled-plugin-version.py` 在位），在隔离目录内写文件不污染主工作树（`git status` 无新增），目录已被 gitignore 覆盖。
